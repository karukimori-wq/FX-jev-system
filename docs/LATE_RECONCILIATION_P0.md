# P0：確定済み注文への追加約定と保留解除（DEMOモックのみ）

## 対象と安全境界

`fxjev/late_reconciliation.py` の `reconcile_late_demo_fill()` は、**すでにFILLED/CANCELEDとして確定済みのDEMO注文**に後から模擬約定が見つかった場合、完全な模擬証拠と整合する範囲で **入金・出金・発注を伴わず** SQLiteの建玉残高とリスク数量を更新する保守的な再照合器。

このモックの `reviewer_id` / `review_ref` は呼び出し元が自由に記入できる監査ラベル。**認証済み管理者承認ではない**。入力された「履歴が完全」とする真偽値もブローカーAPIによる真正性確認ではないため、**実FX口座には接続不可**。

LIVEモードはこの再照合処理で常に拒否する。

## 初回の追加約定訂正の条件

- 元の注文の `account_id`、ロジック、run、mode、client ID、broker order ID、要求数量、最終状態が、当初記録と一致する。
- `ReconciliationProof` の注文・約定・建玉証拠がすべて揃い、鮮度・時刻・数量の整合がとれる。
- **新しい累計約定数量が以前の記録より厳密に増えている**。元注文の要求数量を超えず、最終状態を恣意的に変更しない。
- 再照合対象の注文に保留 `mock_event_holds` があり、同じclient IDで受信した約定ID・broker order ID・数量がすべて新しい証拠に含まれる。
- 口座／モードを取り違えたイベント、同一約定IDの衝突、古いスナップショット、イベント受信前のスナップショットがない。
- **過去の決済注文・部分決済が1件でも記録されている場合は、保留を解除しない**。決済履歴を含むフルライフサイクルの再照合は未実装。
- 初回の既知建玉残高が改変されていない。既存位置がない場合は、従来の累計約定数量が0であることが必要。

## 原子的な訂正

`Ledger._tx()` の1つのSQLiteトランザクション内で次の作業を行う。

1. 注文台帳の最終確定と、最初の `reconciliation_audit` の原記録を検証（**この原記録は上書きしない**）。
2. 受信済み `mock_fill_inbox` と新しい模擬履歴を突合し、過去決済や矛盾がないことを確認。
3. 建玉残高を `position_balances` へ追加または増加させ、同じトランザクションで `orders.filled_quantity` を増加。
4. 追記専用 `mock_terminal_revisions` に訂正前／後の数量、模擬レビュアーID・参照ID・証拠ハッシュを永続記録。
5. 同じ注文に属する `mock_event_holds` のみ削除（他の注文・口座の保留は残る）。

不整合があればトランザクションをロールバックし、以前の状態・リスク保留・監査を保持する。

**保留を解消しても新規注文受付は自動再開しない**。デモ専用 `TradingRuntime.approve_demo()` を別に実行する必要がある。

## 未実装・本番採用禁止の理由

1. 最初の `reconciliation_audit` は約定累計とSHA-256を記録するが、元の約定ID一覧は保存していない。元のすべての執行IDを暗号学的に再証明できない。模擬の「全量履歴」申告は実ブローカー証拠の真正性を保証しない。
2. 追加約定の発生前から部分決済・全決済があるケースは**拒否**する。過去決済分を含む累積建玉残高の一意な再照合・タイムライン再構成が必要。
3. 注文が最初にFILLEDとして要求数量全量を約定済みの場合、さらに増える約定は要求数量を超えるため**拒否**し、安全な保留を継続。
4. 口座のネットポジション、銘柄・売買方向・FXロット換算、証拠金・損失上限、多通貨リスクの照合は未実装。
5. 認証済み管理者の承認、ブローカーの監査可能な履歴取得、イベント欠落・遅延/順不同の完全性証明、複数ホスト/プロセスのフェンシングは本番向けには未実装。
6. このPoCを迂回する既存 `Ledger` の旧APIは初回モックランタイム起動前に呼び出せる。実運用の唯一の発注入口は別途強制する必要がある。
