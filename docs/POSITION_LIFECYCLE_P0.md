# P0 建玉残高・部分決済・全決済 PoC

## 目的と範囲

実ブローカーを使わず、注文照合済みの建玉を、取引口座ID・戦略ID・run ID・取引モード・元注文ID・ブローカー注文IDへ紐付けて記録する。決済の**模擬証拠**が整合した場合に限り、リスク予約から決済済数量を引く。

**このコードは実発注・実決済・ブローカーAPI・実運用機能ではありません。** 各完全性フラグと証拠データは呼び出し側が供給するため、真正性は未保証です。

## データモデル

- orders.account_id: 取引口座ID。既存P0データの移行時のみ `legacy` を付け、口座同一性は推定しない。
- position_balances: client_id を主キーに、account_id, strategy_id, run_id, mode, broker_entry_order_id, opened_quantity, remaining_quantityを記録。
- position_close_batches: 決済注文IDと最終ステータス、要求数量、約定数量、決済後残高、模擬証拠SHA-256を記録。
- position_close_executions: (account_id, execution_id) 一意。決済約定の重複取り込みを拒否。

## リスク予約ルール

1. RESERVEDとUNKNOWNの注文は従来どおり全要求数量を確保し、UNKNOWNが同一モードに残る場合は新規予約停止。
2. 最終確定注文は、登録したposition_balances.remaining_quantityをリスクとして算入する。まだ建玉台帳を持たない過去注文は、従来のfilled_quantityを保守的に保持する。
3. 決済証拠の注文・約定履歴・残建玉スナップショットが全て一致し、注文の最終ステータスがFILLED/CANCELEDである場合だけ残高更新する。
4. 部分決済は実際の約定合計数量だけ減らし、全決済はゼロにする。どちらも既存建玉の所有者・取引口座ID・モードが一致しなければ拒否。
5. SQLite BEGIN IMMEDIATE トランザクション内で決済実行IDの一意性を保証し、証跡と残高更新を原子的に記録する。競合・再送・証拠不足なら全件ロールバック。
6. ロジックの新規エントリー停止中でも、既存建玉の残高照合は処理できる。模擬決済入力は売買指示ではない。

## 対応コード

- `fxjev/ledger.py` — 口座属性付き注文予約、建玉テーブル、リスク予約照会、既存DB移行、建玉決済呼び出し
- `fxjev/reconciliation.py` — 注文/約定/建玉の3情報を検証後、元注文に帰属する建玉を原子的に初回登録
- `fxjev/positions.py` — 閉じた注文の状態、数量、約定ID、所有者、残高、鮮度をチェックし残高と監査記録を更新
- `tests/test_positions.py`, `tests/test_migration.py` — 部分/全決済、再起動・並列決済、旧DB、口座誤帰属、証拠不足と重複を検証

実行: `python -m unittest discover -s tests -v` （CIでも実行）

## 本番に残る必須課題

- **取引口座単位の独立した上限設定・UNKNOWN停止**：今は各戦略の上限は取引口座をまたぎ集約され、UNKNOWN停止は同じモード全体にかかる。安全側だが、本番の口座ごとの仕様は未達。
- **実ブローカーによる証拠の認証・完全性保証**：callerが作れる証拠でリスク枠を解除できるため、現コードを本番APIへ接続してはいけない。
- **実口座のポジション帰属**：口座全体のネットポジションからの推定は禁止。個別建玉へ厳密に帰属できない場合、更新を拒否する。
- **原本が旧PoCの最終注文**：建玉台帳がない過去注文は数量を自動解放しない。検証済み照合と安全な移行が必要。
- **遅延イベント・部分決済の途中状態・サーバー異常終了・分散ホスト**：未検証。
- **既存建玉を守る実決済/損切り処理・口座照合・管理者承認・監査UI**：未実装。

詳細設計312問を逸脱しない。Jev AIはロジックが提示する選択肢IDをひとつ選ぶのみ。別途承認まで main 反映、ブローカー接続、実売買は禁止。
