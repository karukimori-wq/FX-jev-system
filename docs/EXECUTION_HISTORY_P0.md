# P0：初回約定IDの完全保存と訂正履歴の連鎖検証

## 対象・制限

ブローカー非接続のSQLite安全PoC。入力は呼び出し側が用意した**未認証の模擬証拠**であり、実注文/実決済/建玉保護・管理者本人認証は行わない。

今回新設した `fxjev/execution_history.py` は、初回の注文確定時からエントリー側の**全約定IDと数量**を保存し、その後の増分訂正を前回ハッシュにつなぐ。DEMOの追加訂正は `late_reconciliation.py` / `lifecycle_reconciliation.py` と連動する。従来の初回注文照合・モック決済の検証にもIDを利用するが、LIVEでの実売買は一切有効化しない。

## 永続テーブル

- `entry_executions`: client ID、account ID、mode、broker order ID、execution ID、約定数量、最初に証拠を記録した時刻、first_version。1つの(client ID, execution ID)を一意とし、同じ(account ID, mode, execution ID)を他の注文へ使い回せない。
- `entry_revision_chain`: (client ID, version)で初回version 1から連番。種別initial/late-no-close/late-with-closes、累計約定数量、証拠SHA-256、当該versionまでの全約定行のスナップショットSHA-256、前versionのハッシュ、現在の連鎖ハッシュ、記録時刻。
- 従来の `reconciliation_audit` は初回確定の原証拠ハッシュ・数量として引き続き保存。新しい初回約定IDテーブルのgenesisと照合する。
- 従来の `position_close_executions` は決済側IDの元記録として保持。エントリー/決済の同一約定ID利用を拒否し、決済検証時にはエントリーの全ID履歴を検証する。

## 原子的な書き込み

初回の`reconcile_order()`は、SQLiteの同じトランザクションで初回監査、全エントリー約定ID、version 1連鎖、注文状態・数量、元建玉を登録する。何らかの検証・UNIQUE制約が失敗すれば一括ロールバック。

増分DEMO再照合は、**従来の全IDが新しい証拠から欠落していないこと、既存IDが違う数量・broker order IDで上書きされていないこと、新しいIDが過去の決済約定IDや他注文と重ならないこと**を確認する。新たな約定IDをfirst_versionで追記し、対応するversionのスナップショットと前versionの連鎖ハッシュを保存。建玉・元注文数量の訂正と同一トランザクションで実行。

## 連鎖の読み取り検証

`verify_entry_lineage(db, client_id)` は、初回監査との一致・所有口座/モード/注文の一致・すべてのversion連続性・前ハッシュの一致・当該version時点の約定ID全件・数量合計・スナップショットハッシュ・現在注文の累計を再計算する。旧データの改変や途中versionの欠損で失敗し、追加訂正と模擬決済のリスク解放を拒否。

以前の保存方式のSQLiteファイルにある、初回約定IDが記録されていない注文は**自動補完しない**。ゼロ約定も、新方式で確定した場合だけversion 1・ゼロ件の約定履歴を残す。既存の履歴欠損注文には手動照合・隔離が必要。

## 確認済みの挙動

- 初回の全ID・数量・口座IDを保存し、再起動後も検証できる
- 最初の増分訂正と複数回のDEMO増分訂正で、version 1→2→3の連鎖が残る
- 同じIDの数量変更、ID欠落、他注文による再利用、決済約定IDとの衝突、初回監査の書き換え、約定行の改変、前ハッシュの改変を検出
- 部分・全決済の原監査は変更しない。新しい会計ジャーナルは、記録済みの処理確定順で訂正と決済が交互に発生しても再生・検証できる。[会計ジャーナル仕様](ACCOUNTING_JOURNAL_P0.md) を参照。
- 訂正後の新しい決済と再訂正はDEMOモックの会計処理順で検証済み。ただし、実際の市場約定時刻や未受信イベントの完全な時系列証明は未対応。
- 約定IDの欠落した旧DBでは、新しい訂正・決済によるリスク解放を拒否する

## 限界・本番利用禁止

1. この連鎖は**署名・HMAC・外部不変ストレージなしの単純なSHA-256**。SQLiteを任意変更できる攻撃者が全ハッシュを再計算した場合を防げない。真正性・改ざん不可能性の保証ではない。
2. 既知IDの実行時刻は初回記録を保持するが、後続の模擬履歴で同じIDの時刻が一致することまでは要求しない。ID/数量/ブローカー注文IDを中心に検証。厳密な時刻照合は認証済み外部証拠と時系列モデルが必要。
3. 初回の旧DB資産について保存されていなかった約定IDを復元できない。**無根拠な自動バックフィルは禁止**。
4. 今後の模擬決済は`position_close_executions.executed_at_ns`へ実行時刻を保存する。旧DBの時刻はNULLで推定補完しない。なお市場約定時刻の真正性・完全な外部時系列証明は未実装。
5. 外部FXブローカーの全量証拠取得、口座所有認証、資金/証拠金リスク、ネットポジション帰属、送信とDBの原子性、分散フェンシング、管理者本人承認は未実装。
6. モックの完全性フラグとreviewerラベルは外部の真実を保証しない。実口座やLIVEへの接続は禁止。
