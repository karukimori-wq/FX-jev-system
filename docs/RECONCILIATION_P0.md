# P0 UNKNOWN注文照合・復旧 PoC

## 対象
実ブローカーに接続しない構造化された模擬証拠を用い、UNKNOWN注文のリスク予約を不当に解除しないことを検証する。

## 必須証拠
- 最終確定した注文履歴：client ID・broker order ID・ロジックID・run ID・取引モード・数量・最終状態
- 完全な約定履歴：重複のないexecution IDと数量、broker order IDの一致
- 当該注文に帰属する建玉スナップショット：所有者・数量・30秒以内の鮮度・最終注文状態からの時間整合
- 注文履歴、約定履歴、建玉それぞれの全量取得成功

FILLEDなら約定合計＝注文数量。CANCELEDなら約定合計は注文数量以下。本PoCは未決済の新規建玉注文のみ対象とするので、当該注文由来の保有建玉数量＝約定合計を必須とする。

## フェイルクローズ
- 証拠欠損、所有者不一致、鮮度不足、重複約定ID、数量不一致では状態・予約を変更しない。
- UNKNOWNが残る取引モード全体の新規予約を停止する。取引口座IDが未導入のため、停止範囲は意図的に広い。デモとliveは分離する。
- 検証が成功した注文だけSQLiteトランザクションで状態更新とSHA-256証拠ハッシュの永続化を行う。
- 以前のevidence_complete=Trueだけによる解消APIは削除。現在はledger.reconcile(client_id, proof=ReconciliationProof(...))。
- 決済後の建玉リスク解放は未実装で、既存リスクを保守的に保持する。

## 本番に向けた未解決事項
1. 模擬証拠の取得成功フラグだけでは、実ブローカーの真実性・完全性は保証できない。認証済みAPIでの取得と照合が別途必要。
2. ネッティング口座の注文単位ポジション帰属、建玉差分・相殺・部分決済・遅延イベントの安全な取扱いは未実装。
3. 取引口座ごとの予約・停止範囲、複数プロセス障害、強制終了と分散制御の検証は未実施。
4. 実口座接続、実発注、実取引、管理者による再開承認、運用監視は未実装。承認なしに運用しない。
