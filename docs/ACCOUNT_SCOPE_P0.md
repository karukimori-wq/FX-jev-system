# P0 口座別リスク分離・旧台帳保護（モック）

## 対象・安全境界

これは SQLite 内の注文予約と建玉残高の**発注前の安全制御PoC**です。ブローカー口座への接続、認証、実発注、実決済、実取引の承認・運用を行いません。

現時点の口座区切りキーは `(account_id, mode)` です。取引口座IDは内部識別子として信頼済みの呼び出し側が管理する想定です。口座の真正性・所有権確認は未実装です。

## データモデル

- `account_limits(account_id, mode)`: 口座＋取引モードの合計数量上限、停止設定、設定版。
- `account_strategies(account_id, strategy_id, mode)`: 口座＋ロジック＋モードの数量上限、停止設定、設定版。
- `orders.account_id`: 新しい予約と既存の口座ID付き約定を正確な口座に帰属させる。
- `position_balances.account_id`: 元注文・ロジック・実行・モードの所有者を保持したまま建玉残数を管理。

## 新しい口座の登録手順（モック）

1. `account_version = ledger.configure_account("acct-A", Mode.LIVE, 12)`
2. `strategy_version = ledger.configure("alpha", Mode.LIVE, 7, account_id="acct-A")`
3. `ledger.reserve("unique-id", "alpha", "run-1", Mode.LIVE, 2, strategy_version, account_id="acct-A", expected_account_version=account_version)`

口座上限とロジック上限は **BEGIN IMMEDIATE** の同一SQLiteトランザクションで両方を確認・予約します。両方の安全設定バージョンが一致しない場合、またはどちらかが停止中の場合、新しい予約を拒否します。

`account_exposure(account_id, mode)` は口座合計の予約・建玉残数を返します。`active_exposure(strategy_id, mode, account_id=...)` は指定口座内のロジック別数量を返します。account_id を省略すると、従来互換のため全口座合計を返します。

### UNKNOWN注文と停止範囲

新しい**明示登録済みの口座**では、UNKNOWNがその `(account_id, mode)` 内にあるときだけ新規予約を停止します。他口座と別モードの予約は独立します。ただし「帰属不明の旧注文」が残る場合は例外です。

### 旧SQLiteデータの移行

- 以前の `strategies(strategy_id, mode)` は旧注文の外部キー参照として**維持**します。
- 明示的な新口座のロジックを作成するとき、旧外部キー参照用に `max_quantity=0,enabled=0` の旧設定アンカーを必要な場合のみ作成します。**このアンカーによって旧方式で発注可能になることはありません**。
- 旧注文の `account_id='legacy'` は帰属が証明されていないことを意味します。旧注文のリスク残高が同じモードに1以上ある限り、**どの明示的口座でも新規予約をブロック**します。自動割当はしません。
- 旧注文が最終照合で完全取消（約定数量0）と確認されたときだけ、そのリスクに起因するブロックが解除されます。既存建玉を推測で解放しません。
- `legacy` は予約済み識別子で、実口座IDとして使用できません。
- 既存データの口座归属を確認する管理者ワークフローは未実装です。

## 検証

`python -m unittest discover -s tests -v`

テスト領域：同一戦略の別口座分離、同一口座の複数ロジック合計上限、複数run、同時予約の競合、口座ごとのUNKNOWN停止、デモ分離、設定版変更、停止／容量引下げ、旧注文の保守的隔離、旧DBとの互換、途中決済後のリスク残数。

## 本番向け未完了事項

1. 取引口座のAPI認証・所有者照合、外部接続IDの正規化、ブローカー側数量と内部台帳の同期は未実装。
2. 強制終了・遅延イベント・複数ホストでの競合、リアルタイム口座残高・証拠の真正性・予約喪失テストは未完了。
3. 口座横断の全体リスク上限、銘柄・方向・証拠金・含み損など金額ベースの上限は未実装。数量は整数の模擬単位であり、ロット換算は未確定。
4. グローバルなclient注文IDは全口座で一意。既存の監査表もbroker注文IDを全口座で一意とするため、ブローカーによっては保守的に過剰拒否する。
5. 旧DBを本番移行する際はバックアップ、テーブル制約と実口座の帰属検証、ロールバック手順が必要。
6. 既存建玉の実保護、管理者再開承認、安全設定変更と実送信間の原子性は未実装。

Jev AIは戦略が定義した選択肢から1つのIDのみ返し、理由・確信度・数値等は返しません。main反映・実口座接続・実売買は別途明示承認まで禁止します。
