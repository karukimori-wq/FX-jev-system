# P0 モック約定イベントの永続台帳・遅延イベント隔離

## 対象・安全境界

本コードは **認証されていない模擬約定情報** を受け取り、SQLiteに永続化して異常時に取引口座を保留するための検証PoCです。実ブローカーのイベントAPI、WebSocket、発注API、管理者認証、実注文や建玉の保護処理はありません。

取引実行の許可、資金リスクや本番稼働の保証を与えるものではありません。ライブ取引は常に禁止します。

## モデルと処理

新規: `fxjev/events.py` の `FillNotice`、`ingest_mock_fill(ledger, notice)`。

- 1イベントは account_id / mode / client_id / broker_order_id / execution_id / quantity / occurred_at_ns を持ちます。
- `mock_fill_inbox`: `(account_id,mode,execution_id)` を一意とし、証拠内容のSHA-256、観測数量、受信時刻を保持。
- 完全に同一のイベント再送は `duplicate` として扱い、リスク数量・監査件数を二重加算しません。
- 同一IDで内容が異なる場合は `mock_event_conflicts` に衝突を記録し、監査と口座停止を**コミットした後で** `SafetyError` を返します。矛盾があったことをトランザクションの例外で消しません。
- `mock_event_holds`: 注文がない孤立イベント、所有者・口座・モード不一致、最終確定後に届いた新しいイベント、重複ID衝突などを、口座・モード・client_idごとに保持します。ゲートが開いている場合には同一SQLiteトランザクションで失効。
- 新規イベントが未確定 `RESERVED` 注文に対応するなら `UNKNOWN` に変更し、リスクを保持。事前のブローカー送信有無は推定しません。

## リスクを過少評価しないための保守的ルール

保留のある既知注文の算入数量は、原則として次の**大きい方**です。

1. 元の注文要求数量
2. 現在の既知建玉残高（または記録済み約定数量）＋当該注文について受信した模擬イベントの約定数量合計

この数量は監査上の保守的な上限見積りであり、証拠金・資金・実際の保有建玉を表す値ではありません。イベントは既存の約定履歴と重なる可能性があるため、意図的に多めに見積もります。

**新規イベントの受信後は該当口座・modeの新規注文予約を拒否します。** すでに以前の予約が通っていた場合にそれを遡って取り消すことはできません。古い注文の保護機能も実装していません。

口座未確認の孤立イベントには既知注文がないため数量を算定できません。この場合も新規予約は停止し、既知残高をゼロとして安全を宣言しません。

## 初回注文の照合との連携

`fxjev/reconciliation.py` に以下の制約を追加しました。

- 保留中の初回注文を最終確定する際、同一client IDについて受信した全イベントの execution ID・broker order ID・約定数量を、完全な模擬証拠の約定履歴と突合。
- 未収録の模擬イベント、誤った所有口座・取引モード、衝突した約定IDが残るなら、最終確定と予約解放を拒否。
- 全イベントが正しく含まれ、最終状態・約定・個別建玉が一致するときのみ、その初回注文に関連する保留を削除。保留解消後も管理者の新規承認が必要なケースではゲートは自動再開しません。
- **すでに最終確定した注文に新しい約定情報が来た場合は再確定を自動実行しません。** 新イベントの保留と高めのリスク見積りを保持します。実ブローカー履歴に基づく再照合・状態訂正は別工程です。

## 残る本番用課題

1. ブローカーの認証済みイベントチャネル・イベント順序・欠落検出、取得再試行、口座と約定IDの真正性証明。
2. 遅延・増分約定を実際の建玉と対比し、数量・ポジションの訂正を安全に適用するフルリコンシリエーションと口座保留の管理者承認付き解除。
3. 実際のブローカーから到着していないイベントや遅れて到着するイベントを、現在のモックだけで予見することはできません。
4. 市場価格、資金・証拠金・損失率、買い/売り別建玉、複数口座間の総リスクと含み損など、金額・方向を考慮した上限は未実装。
5. 外部APIのイベント受信と内部DB更新の原子性、複数ホスト間のフェンシング、障害通知、承認者本人認証、実損切り・決済・保護注文は未実装。
